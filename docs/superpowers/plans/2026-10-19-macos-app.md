# Lapka macOS App Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Deliver a locally buildable Lapka.app with bundled Node and a WebKit player window.
**Architecture:** A native AppKit owner starts a desktop-only Node entry point over a private parent/child pipe, then loads its readiness URL in WKWebView. Persistent data lives outside the bundle. The existing browser entry remains usable.
**Tech Stack:** Swift/AppKit/WebKit, Node.js 24.13.0, existing vanilla JS frontend.
**Spec:** docs/superpowers/specs/2026-10-19-macos-app-design.md

## Global Constraints

- macOS 13.5 or newer; separate arm64/x64 bundles. Verify arm64 locally.
- Default desktop loopback port 18800; never kill or attach to unrelated servers.
- Data outside .app/npm cache; preserve browser .dev defaults.
- No npm publication, GitHub Release or installation into /Applications.

## Review Focus

- A conflicting port must leave the existing service alive.
- A parent crash must not leave a hidden server.
- A repeat launch must not create duplicate windows/servers.
- Paths containing spaces and an application moved after build must still work.
- The player Quit action must terminate the native owner, while the normal window close must allow Dock reopening.

## Results

Implemented on codex/macos-app, based on codex/airplay@5ef10eb. Nine desktop/packaging tests pass. Native acceptance verifies real WKWebView media, seek/pause, AirPlay API exposure, canceled navigation, close/reopen, player Quit and parent EOF cleanup. The complete Node suite has 59 passing tests and the same ffmpeg-dependent library/subtitle setup failures as the starting branch. Frontend check, bundle signature and ZIP integrity pass.

Rulings: use stable port 18800 to preserve localStorage origin; set minimum macOS to 13.5 to match the actual bundled Node deployment target; refuse overwriting a running app. The final artifact is under dist/macos-arm64-verified because an earlier build is already in use. No active user session was stopped or replaced. Real receiver transport, Intel execution and notarized public distribution remain outside verified evidence.

## Integrated macOS window controls

Approved follow-up on the same branch: remove the separate title row, preserve actual AppKit traffic lights, reserve space inside the existing header, and drag unused header space. Use a full-size content view with a transparent unified titlebar; inject native-only layout and report interactive DOM rectangles to a transparent AppKit drag view. Keep browser layout unchanged.

Regression first: native smoke failed with “native title bar still consumes a separate row” before implementation. Acceptance now checks full-height web content, native control frames, toolbar collisions (including a three-digit save counter) at 1280/1000/520 points, narrow/open/closed queue states, the actual view hierarchy for drag hit regions, native fullscreen entry/exit, media playback and lifecycle. Nine server/packaging tests and frontend checks pass. Review addressed unnecessary geometry work during playback and fullscreen state after reload.

Visual preview used a separate bundle identifier, ephemeral WebKit storage and a temporary server directory. CUA delivered mouse-down to the drag view but Window Server did not move the background test window; physical dragging remains for a user check. No active user session was stopped or replaced. Updated artifacts are under dist/macos-arm64-integrated.

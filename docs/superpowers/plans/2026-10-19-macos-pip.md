# macOS video PiP repair

User report: the native application shows “Browser refused PiP”. Reproduced with
an AVFoundation-generated H264 MP4 in the actual WKWebView: the DOM API reports
enabled, but the request rejects with NotSupportedError and video presentation
support is false. macOS WebKit defaults AllowsPictureInPictureMediaPlayback to
false; its public WKWebViewConfiguration switch is iOS-only.

The host opts into the WebKit preference only when its Objective-C setter exists.
The guarded SPI dependency is documented in both READMEs. No frontend API shim or
change to browser playback was necessary.

Native acceptance failed before the fix and passes after it. The harness now
uses an actual generated video track, rather than audio in a video element. It
checks PiP opening, returning to the same position, reopening during playback,
and UI cleanup after native close. All native lifecycle/chrome checks, nine
desktop/packaging tests, frontend checks and diff whitespace checks pass. Focused
review found no actionable issues.

Build was staged under .dev/macos-update to avoid registering duplicate app
bundles. The user explicitly closed Lapka and authorized updating the remaining
dist/macos-arm64-integrated bundle and its ZIP. Library/settings stay outside
the replaced application bundle.
